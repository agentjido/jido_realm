## Goal Capsule

Give an agent one API for running work in a Realm and separate the lifetime of a service from access to its port. Keep existing integrations working through the same session.

## Product Contract

### Summary

The host binds a Realm to a provider, grants capabilities, and registers commands and services. The agent uses the same calls on each provider.

### Problem Frame

Entry points, background runs, coding tools, and trusted commands have separate session paths. Checked previews combine service startup with access. Container checks assume a Mix project.

### Actors

Agent action, host configuration, Realm session, execution and service adapters, and host gateway.

### Requirements

- R1. Use `Realm.exec` for entry points, Bash commands, and named commands. Keep existing calls and their result shapes.
- R2. A supplied request ID supports replay, status, and conflict detection. Preserve output bounds and cleanup fences.
- R3. Start and stop a named service independently of opening and closing a port route. Allow the host to require a successful check for the source used to start the service.
- R4. Use the same calls to run checked Phoenix and TypeScript services in Docker and Apple Container. Keep application and toolchain settings in host configuration.

### Key Flows

Discover a command, run it, and recover a reply by ID. Start a service from a successful check, expose a port, close the route, and stop the service. Close the Realm to release owned resources.

### Acceptance Examples

Replay a completed check with the same ID. Refuse changed arguments and stale source. Confirm a service has no gateway route until one is exposed. Confirm closing a route leaves the service available for a new route.

### Success Criteria

The compatibility suite passes. Each container engine serves the expected HTTP result using the common API. The live local model test checks the coding workflow if LM Studio is available.

### Scope Boundaries

Local changes and verification only. Preserve existing file, transfer, artifact, provider, and agent contracts. The service contract starts with one active service and one configured HTTP port per session.

### Key Decisions

Keep run state in the lease-owning session. Resolve registered commands through host configuration. Keep the host gateway responsible for viewer identity and route access.

### Rejected Alternatives

Separate APIs for each workload or engine would duplicate admission and recovery. Accepting a caller-supplied bind address would bypass host policy.

### Dependencies

Docker, Apple Container, cached local images, and LM Studio for the live edit test.

### Outstanding Questions

No open decision prevents implementation. Multi-service scheduling and additional port protocols require their own adapter and lifecycle contracts.

### Sources

Current Realm facade, Session, Runner, Preview, coding request and container runner modules, and the existing coding and workspace integration tests.

## Planning Contract

### Product Contract Preservation

Keep the current coding actions, invoke grants, checked preview behavior, and trusted host preview adapter. Add the public API before changing caller examples.

### Current System

Session has separate coding and background state. The coding runner stages source and also owns both engines' CLI details. A preview allocates its route on startup.

### Target System

One run registry and common dispatch. An independent route refers to a running service. A shared staged runner uses generic host options and engine-specific adapters.

### Key Technical Decisions

- KTD1. Use tagged execution requests. Check grants before replay. Keep explicit requests bounded and retain unresolved outcomes.
- KTD2. A check records the snapshot identity. Service startup compares the verified snapshot to the staged source before launch.
- KTD3. Only the host selects the guest port and network policy. Engine loopback bindings are transport for the gateway.

### System Boundaries and Change Surface

Public Realm API, Session, Commands, runner adapters, gateway lookup, package docs, and integration fixtures.

### Implementation Units

1. U1 implements R1 and R2. Consolidate request preparation, dispatch, progress, status, and replay.
2. U2 implements R3. Separate service ownership and route access. Preserve existing preview calls.
3. U3 implements R4. Separate engine transport from staging and move workload settings to fixtures.
4. U4 verifies the contracts with default, provider, and live tests.

### Work Graph

U1 supplies the check result to U2. U2 and U3 define the provider acceptance path. U4 checks all units.

### Verification Contract

Run formatting and the default tests. Test conflict and replay, grant checks, stale source, route revocation, independent service lifetime, and provider cleanup. Run Docker, Apple Container, and the local model suite when their dependencies are available. Record which tests ran.

### Rollout and Recovery

Keep the existing call forms and host options during migration. Retry confirmed cleanup with the existing lease controls. Do not release the lease after an unknown run until reconciliation confirms termination.

### Risks and Assumptions

Docker and Apple Container require a loopback transport at creation. Opening a Realm port authorizes a gateway route to that transport. The host is the trust boundary for loopback.

### Open Planning Decisions

Keep storage and provider expansion outside this change.

### Definition of Done

The common caller examples work on both engines, legacy tests pass, and the test record identifies external checks that could not run.

`lib/jido_realm.ex`, `lib/jido_realm/session.ex`, `lib/jido_realm/runner/`, and `test/integration/09_model_driven_files/`.
